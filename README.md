# Mini NPU Simulator

MAC(Multiply-Accumulate) 연산으로 십자가(Cross)와 X 패턴을 판별하는 Python 콘솔 시뮬레이터입니다.
외부 라이브러리 없이 표준 라이브러리만으로 3×3 ~ 25×25(그 이상도 가능) 크기의 패턴을 처리합니다.

---

## 1. 실행 방법

```bash
# Python 3.8 이상, 외부 라이브러리 설치 불필요
python main.py                          # 메뉴에서 모드 선택 (1/2/3)

python main.py --mode 1                 # 사용자 입력 (3×3)
python main.py --mode 2                 # data.json 분석 (기본: main.py와 같은 폴더의 data.json)
python main.py --mode 2 --data data_error_cases.json   # 의도적 오류 케이스 분석
python main.py --mode 3                 # 패턴 생성기 (보너스)

python -m unittest discover -s tests -v # 단위 테스트 37개
```

| 모드 | 입력 | 출력 |
|---|---|---|
| 1. 사용자 입력 (3×3) | 필터 A, 필터 B, 패턴을 한 줄씩(공백 구분) | A/B 점수, 연산 시간(10회 평균), 판정(A / B / 판정 불가), 3×3 성능 표 |
| 2. data.json 분석 | `data.json` (또는 `--data 경로`) | 케이스별 Cross/X 점수·판정·PASS/FAIL → 성능 표(3/5/13/25) → 결과 요약 |
| 3. 패턴 생성기 (보너스) | 크기 N (3 이상 홀수, 여러 개 가능) | 생성한 Cross/X 패턴 판정 + 크기별 성능 표 |

**모드 1 입력 팁**
- 필터·패턴의 첫 줄에 `cross`(또는 `+`)나 `x`를 입력하면 생성기가 3×3 Cross/X를 자동으로 만듭니다 (보너스 생성기 재활용).
- 열 개수 불일치, 숫자 파싱 실패, 빈 줄(행 누락)이면 `입력 형식 오류: 각 줄에 3개의 숫자를 공백으로 구분해 입력하세요.`를 출력하고 **그 줄만** 다시 입력받습니다.
- 행은 정확히 3줄을 순서대로 받기 때문에 행 개수는 입력 구조로 보장되고, 빈 줄은 행 누락으로 보고 재입력을 유도합니다.

## 3. 구현 요약

### 데이터 구조 — `Matrix`
- N×N 2차원 리스트를 저장하고, `get(r, c)` / `set(r, c, v)`로 특정 위치 값을 읽고 씁니다.
- `Matrix.from_rows()`가 **정사각형 여부(행/열 개수), 숫자 타입(bool·문자열 거부), 유한값(NaN/Infinity 거부)**을 검증합니다.

### 라벨 정규화
| 원본 표기 | 등장 위치 | 표준 라벨 |
|---|---|---|
| `'+'`, `'cross'` (대소문자·앞뒤 공백 무시) | expected, 필터 키 | `Cross` |
| `'x'` | expected, 필터 키 | `X` |

정규화는 로드할 때 한 번만 하고, 이후 모든 비교와 출력은 **표준 라벨(`Cross`/`X`)로만** 합니다.
해석할 수 없는 라벨(예: `'o'`)이나 expected가 없는 경우는 해당 케이스를 FAIL로 처리합니다.

### MAC 연산
- `mac(pattern, filter)`: 이중 `for` 반복문으로 같은 위치끼리 곱해 누적 → `float` 점수 (곱셈 N²회)
- `mac_flat(a, b)` (보너스): 길이 N²인 1차원 리스트를 단일 반복문으로 처리

### 점수 비교 정책 (epsilon)
```python
EPSILON = 1e-9
if abs(score_a - score_b) < EPSILON:  -> UNDECIDED (모드 1: "판정 불가")
else:                                 -> 점수가 큰 쪽의 라벨
```
모드 2에서 `UNDECIDED`는 expected(Cross/X)와 같을 수 없으므로 항상 FAIL입니다.

### 스키마 검증 (모드 2) — 케이스 단위 FAIL, 프로그램은 중단되지 않음
모든 오류는 **케이스 단위 FAIL**로 바꾸고, 요약에서 원인을 3가지로 분류합니다.

| 분류 | 예시 |
|---|---|
| `데이터/스키마` | 키 형식 오류, `input`/`expected` 누락, 비정사각형, 숫자가 아닌 값, 키의 N ≠ input 크기, 필터 누락·손상, 해석할 수 없는 라벨 |
| `수치 비교·동점` | \|Cross − X\| < 1e-9 → UNDECIDED |
| `판정 불일치` | 판정은 정상이지만 expected와 다름 (라벨 또는 로직 점검 필요) |

파일 없음, JSON 문법 오류, `filters`/`patterns` 누락 시에도 안내를 출력하고 정상 종료합니다.
마지막 안전망 `except Exception`이 예상하지 못한 예외도 케이스 FAIL로 바꿉니다.

### 시간 측정
- `time.perf_counter()` 사용, **`mac()` 호출 구간만** 측정 (입력·출력·파일 읽기 제외)
- 워밍업 1회(측정 제외) → **10회 측정 평균**(ms)
- 측정 중에는 GC(가비지 컬렉션, 파이썬의 자동 메모리 정리)를 꺼서 튐을 줄입니다 (`timeit`과 같은 방식)

### 보너스
1. **패턴 생성기**: `generate_cross(n)` / `generate_x(n)` (3 이상 홀수). 모드 1(`cross`/`x` 입력), 모드 3, 성능 분석 입력(3×3과 data.json에 없는 크기)에 재활용합니다.
2. **1차원 최적화**: `Matrix.to_flat()` + `mac_flat()`. 같은 입력·같은 반복 횟수로 두 버전을 모두 측정하고, 표에 향상 배율과 **결과 일치 여부(2D == 1D)**를 함께 출력합니다. 행 우선(row-major) 순서로 펼치기 때문에 누적 순서가 같아 결과가 비트 단위로 같습니다.

|---|---|---|---|---|---|---|---|

| size_13_1 | 0.3 | 14.700000000000008 | 14.4 | X | `x` → X | PASS | X |

| size_25_1 | 4.9 | 4.899999999999999 | 1.78e-15 | UNDECIDED | `x` → X | **FAIL** | Cross (오판) |

### 4-2. 실패 원인 분석

**(1) 분류: 3건 모두 "데이터/스키마"나 "로직"이 아니라 "수치 비교" 문제입니다.**
- 스키마: 모든 키가 `size_{N}_{idx}` 형식이고, 필터는 5/13/25 정사각 행렬이며, 키의 N·패턴 크기·필터 크기가 모두 일치합니다.
- 라벨: 원본 `'+'`, `'x'`, `'cross'`를 모두 `Cross`/`X`로 정규화했기 때문에 라벨 때문에 실패한 케이스는 없습니다.
- 로직: 2차원 `mac()`과 1차원 `mac_flat()` 점수가 모든 케이스에서 비트 단위로 같고, 점수가 손계산과도 일치하므로 MAC 로직 문제가 아닙니다.

**(2) 직접 원인: 실제로는 같은 값(동점)인데, 부동소수점 오차 때문에 아주 조금 달라 보입니다.**
- size_5_1: Cross 필터 중심 가중치 0.9 × 1 = **0.9**. X 필터는 0.1짜리 가중치 9개를 더해 0.1 + 0.1 + …(9회) = **0.8999999999999999**.
  0.1은 2진수로 정확히 표현되지 않아(약 0.1000000000000000055…) 더할 때마다 반올림 오차가 쌓입니다.
- size_13_2: 0.3을 25번 더한 값 = **7.499999999999997**, X 필터 중심 가중치 = **7.5**.
- size_25_1: Cross 필터 중심 가중치 **4.9**, 0.1을 49번 더한 값 = **4.899999999999999**.
- 수학적으로는 세 케이스 모두 정확한 동점입니다 (0.9 = 0.9, 7.5 = 7.5, 4.9 = 4.9).

**(3) epsilon이 필요한 이유: `>`로만 비교하면 3건 모두 expected의 *반대*로 판정됩니다.**
- 1e-16 ~ 1e-15 크기의 오차가 승패를 가르기 때문에, "그럴듯하지만 근거 없는 오답"이 나옵니다.
- epsilon(1e-9) 정책을 쓰면 이 경우를 "판단 불가 = UNDECIDED"로 바르게 처리해, 오판을 정직한 '판정 불가'로 바꿉니다.
- 1e-9는 누적 오차(약 1e-15)보다 훨씬 크고 의미 있는 점수 차이(0.1 이상)보다 훨씬 작아서 두 경우를 안전하게 구분합니다.
- epsilon을 키우거나 동점 시 한쪽으로 몰아주는 규칙으로 PASS를 만들면 결과를 왜곡하게 되므로, 명세 규칙(**동점 = FAIL**)을 그대로 유지했습니다.

**(4) 근본 원인: 필터 가중치 합이 불균형합니다 (데이터/필터 설계 문제).**
- 필터 가중치 합: size_5 Cross 8.9 / X 0.9, size_13 Cross 7.5 / X 14.7, size_25 Cross 52.9 / X 4.9
- 동점 3건은 모두 반대 필터의 **중심 가중치(0.9 / 7.5 / 4.9)가 정답 필터의 가중치 총합과 정확히 같습니다**.
  그래서 MAC 원점수만으로는 "잘 맞는 필터"와 "그냥 가중치가 큰 필터"를 구분할 수 없습니다.
- 개선 제안 (명세가 원점수 비교를 요구하므로 미적용): 점수를 각 필터의 가중치 합으로 나누어 정규화하면
  size_5_1 → Cross 0.101 / X 1.0, size_13_2 → Cross 1.0 / X 0.510, size_25_1 → Cross 0.093 / X 1.0으로 **6건 모두 PASS**가 됩니다.
  실제 AI 모델도 가중치 정규화나 편향(bias) 학습으로 이 문제를 다룹니다.

**(5) 라벨 정규화가 막아 준 실패**
- 정규화 없이 원본 문자열끼리 비교했다면(`'+'` vs `'Cross'`, `'x'` vs `'X'`) **PASS 3건을 포함한 6건 전부가 FAIL**이 됩니다.
  스키마 문제인데 로직 버그처럼 보이게 되는 대표적인 경우입니다.

### 4-4. 시간 복잡도 분석 — O(N²)

실측 결과 (`python main.py --mode 3`, 입력 `3 5 13 25 51 101 201`, 10회 평균, 실행 환경마다 값은 달라짐):

| 크기 | 2D 평균(ms) | 연산 횟수 N² | 연산당(ns) | 1D 최적화(ms) | 향상 |
|---|---|---|---|---|---|
| 3×3 | 0.0010 | 9 | 112.5 | 0.0006 | 1.81배 |
| 5×5 | 0.0014 | 25 | 54.7 | 0.0009 | 1.56배 |
| 13×13 | 0.0066 | 169 | 39.1 | 0.0063 | 1.05배 |
| 25×25 | 0.0237 | 625 | 37.9 | 0.0209 | 1.13배 |
| 51×51 | 0.0944 | 2,601 | 36.3 | 0.0859 | 1.10배 |
| 101×101 | 0.3722 | 10,201 | 36.5 | 0.3451 | 1.08배 |
| 201×201 | 1.4131 | 40,401 | 35.0 | 1.3731 | 1.03배 |

- **이론적 근거**: `mac()`은 N행 × N열의 모든 위치를 정확히 한 번씩 방문하며, 위치마다 곱셈 1회 + 덧셈 1회를 합니다. 총 연산은 N²회 → **O(N²)**.
  메모리도 N²개 값을 가진 행렬 2개를 저장하므로 공간 복잡도 역시 O(N²)입니다.
- **실측 근거 1 — 연산당 시간이 상수로 수렴**: 3×3에서는 112 ns이지만, 25×25부터는 **약 35~38 ns로 거의 일정**합니다.
  "시간 ÷ N² ≈ 상수"라는 것은 곧 "시간 ∝ N²"라는 뜻입니다.
- **실측 근거 2 — 증가 비율이 일치**: 101 → 201에서 N은 1.99배, N²은 3.96배 늘었고, 측정 시간은 0.3722 → 1.4131 ms로 **3.80배** 늘었습니다.
  25 → 201에서도 N²이 64.6배일 때 시간은 **59.6배**로, O(N)이었다면 나왔을 8배와는 거리가 멀고 O(N²)의 64배에 가깝습니다.
- **작은 크기에서 벗어나는 이유**: 3×3에서는 함수 호출, `range()` 생성, 타이머 자체의 고정 비용(약 1 µs 미만)이 9번의 연산보다 상대적으로 큽니다.
  그래서 작은 N에서 연산당 시간이 크게 나오고, N이 커질수록 고정 비용이 묻혀 점근적인 O(N²) 특성이 드러납니다.
- **data.json 크기 기준**: 5×5 → 13×13 → 25×25에서 측정 시간은 0.0014 → 0.0069 → 0.0237 ms로, N²이 6.8배·3.7배 늘 때 시간은 4.9배·3.4배 늘었습니다.
- **의미**: 이미지·필터 한 변이 2배가 되면 연산은 4배가 됩니다. 실제 모델은 고해상도 입력에 필터 수천 개를 쓰므로 직렬 처리(CPU)로는 금방 한계에 부딪힙니다.
  NPU는 N²개의 곱셈이 **서로 독립적**이라는 점을 이용해 수천 개의 MAC 유닛으로 동시에 처리하고, P개 유닛이면 실질 시간을 약 O(N²/P)로 줄입니다.

### 4-5. 1차원 최적화 결과 해석 (보너스)

- 같은 입력·같은 10회 반복에서 1D는 **작은 N(3~5)에서 1.4~1.8배 빠르고**, 큰 N(51 이상)에서는 **1.03~1.1배**로 효과가 줄어듭니다.
- 2D 버전은 행마다 안쪽 반복문용 `range()`를 새로 만들고, 원소마다 인덱싱을 두 번(`a[r][c]`) 합니다. 1D는 반복문 하나에 인덱싱 한 번(`a[i]`)입니다.
  작은 N에서는 안쪽 반복문 준비 비용의 비중이 커서 효과가 잘 보입니다.
- 큰 N에서는 원소당 CPython 인터프리터 비용(float 객체 처리, 바이트코드 실행)이 지배적이라 두 버전 모두 같은 상수의 O(N²)에 수렴합니다.
  파이썬 리스트는 float 객체를 가리키는 **포인터 배열**이라, C 언어나 NPU에서 1차원 배열이 주는 캐시 지역성 이득은 잘 드러나지 않습니다.
- 실제 하드웨어(NPU·GPU)에서는 가중치를 연속 메모리에 미리 펼쳐 두면 주소 계산이 단순해지고 버스트·캐시 접근이 가능해집니다. 그래서 1D 변환은 **전처리**로 보고 측정 구간에서 뺐습니다.
- 10 µs 이하 측정은 실행할 때마다 ±20% 정도 흔들릴 수 있습니다 (가끔 향상 배율이 1 미만으로 나오는 것은 잡음). 측정 중 GC를 꺼서 이 잡음을 줄였습니다.

### 4-6. 정리

data.json의 FAIL 3건은 필터 가중치 불균형으로 생긴 진짜 동점을 epsilon 정책이 오판과 구분해 낸 **의도된 결과**입니다.
라벨 정규화로 표기 차이(스키마)에서 생길 수 있는 실패는 모두 없앴고, MAC 로직은 2D/1D 교차 검증과 손계산으로 정상임을 확인했습니다.
